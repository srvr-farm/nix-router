# Pi-hole Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy Pi-hole as the LAN's DNS server (direct-resolver mode, real per-device stats), coexisting with the existing dnsmasq DHCP/local-hostname setup, with two independent quick-disable mechanisms.

**Architecture:** Pi-hole runs as a `pihole/pihole` container (Podman, via NixOS `virtualisation.oci-containers`) on its own macvlan IP (`10.0.0.53`) attached to `br-lan`, avoiding any port-53 conflict with dnsmasq (`10.0.0.1`). DHCP hands out `10.0.0.53` as the DNS server; Pi-hole conditionally forwards `*.callan.local`/`*.srvr.farm`/the `10.0.0.0/24` reverse zone to dnsmasq and forwards everything else upstream after filtering. The DHCP-advertised DNS server IP lives in a runtime-mutable dnsmasq conf-file (same pattern as the `dhcp-hostsfile` migration from the prior change), so `dns-failover` can flip it back to dnsmasq directly without a redeploy if Pi-hole itself is down.

**Tech Stack:** NixOS 24.11, Podman (`virtualisation.oci-containers`), `pihole/pihole:2026.07.2` Docker image, bash (`pkgs.writeShellApplication`), dnsmasq 2.90.

## Global Constraints

- Pi-hole's fixed LAN IP: `10.0.0.53`. MAC (pinned, macvlan default is random-per-restart otherwise): `02:00:00:00:00:53`.
- Direct/bypass DNS IP, for LAN **clients** (`dns-failover bypass` target - dnsmasq on `br-lan`, unfiltered): `10.0.0.1`. Unaffected by the macvlan-isolation issue below - ordinary LAN hosts were never macvlan children and could always reach `10.0.0.1` fine.
- **Pi-hole's own gateway/conditional-forwarding target is `10.0.0.254`, not `10.0.0.1`** (added in Task 2b - see below). macvlan bridge-mode isolates a child (the `pihole` container) from its own parent device's (`br-lan`) IP stack in *both* directions - the router (`10.0.0.1`) can never be reached directly by a macvlan child on the same parent, no matter what. `10.0.0.254` is a second, host-side macvlan interface (`pihole-shim`) on the same parent - macvlan siblings on the same parent *can* reach each other, so this is the only IP the Pi-hole container can actually use to reach anything running on the router itself (dnsmasq, in this case).
  **Correction, post-fix (final-review fix wave, 2026-08-11):** the "router can never be reached directly" claim above describes the general macvlan limitation, but it's no longer true for `10.0.0.53` specifically. Task 2b's `pihole-shim` interface (see below) added an explicit `/32` route for `10.0.0.53` precisely so the router's own network namespace CAN reach the Pi-hole container - `scripts/dns-failover.sh`'s `pihole` subcommand depends on this, probing `10.0.0.53:53` directly from the router's own shell. The general macvlan-isolation limitation still holds for every other address; this is a narrow, deliberate carve-out for the one IP that has a specific route pointing at it, not a change to macvlan behavior generally. See `modules/pihole.nix`'s networking comment for the current explanation.
- Upstream resolvers (match existing dnsmasq config): `1.1.1.1;1.0.0.1;208.67.222.222;208.67.220.220`.
- Local-domain conditional forwarding target (used inside the `pihole` container's own config): `10.0.0.254` (**not** `10.0.0.1` - see above), for `callan.local`, `srvr.farm`, and reverse zone `0.0.10.in-addr.arpa`.
- Image: `pihole/pihole:2026.07.2` (pinned; nixpkgs has no native Pi-hole module - confirmed only a Prometheus exporter exists - so this is a container, not a native NixOS service).
- Deploy command (same as every prior change this session): `nix run github:NixOS/nixpkgs/nixos-24.11#nixos-rebuild -- switch --flake .#router --target-host mark@10.0.0.1 --use-remote-sudo`, run from `/home/mark/source/nix-router` on the dev machine.
- This dev machine is itself a real LAN host (`10.0.0.10`, same L2 segment as the router) - use it directly for `dig`/`curl` verification against Pi-hole's macvlan IP. Do **not** run those checks over SSH on the router itself - macvlan's host-isolation limitation means the router's own shell generally cannot reach a macvlan container's IP, even though every other LAN host can.
  **Correction, post-fix (final-review fix wave, 2026-08-11):** as above, this is no longer literally true for `10.0.0.53` - the router itself can now reach it via the `pihole-shim` `/32` route. The testing convention (verify from `10.0.0.10`, not over SSH on the router) still stands regardless, both because it's the more representative vantage point (an ordinary LAN client, not the router's own specially-routed exception) and because it's still true for every other macvlan-adjacent address.
- All new on-router scripts follow the established style from `scripts/dhcp-static.sh`/`dhcp-leases.sh`/`lan-hosts.sh`: no shebang or `set -euo pipefail` in the script body (supplied by `writeShellApplication`), `usage()`/`die()`/`require_root()` helpers, `--help`/`-h` prints full usage, packaged via `pkgs.writeShellApplication` with `runtimeInputs`.
- Secrets follow the existing `secrets/ddclient.conf` pattern: real files live outside the Nix store, are gitignored individually (not the whole directory), have a committed `.example` template, and are deployed to the router by hand (never through the Nix store, never committed).

- [ ] **Step 1: Create `modules/pihole.nix` with Podman + the macvlan network service**

```nix
{ pkgs, ... }:
let
  piholeNet = "pihole-net";
  lanIface = "br-lan";
in
{
  # Only container workload on this box - Podman avoids running a full
  # Docker daemon for one container, and is the more NixOS-idiomatic
  # default when nothing else already needs Docker specifically.
  virtualisation.podman.enable = true;
  virtualisation.oci-containers.backend = "podman";

  # Pi-hole gets its own MAC/IP on br-lan via macvlan, rather than host
  # networking, so it can bind :53 without colliding with dnsmasq's own
  # :53 on 10.0.0.1 - each has its own IP, no port conflict possible.
  # This does mean the router's own network namespace generally can't
  # reach 10.0.0.53 directly (a well-known macvlan-bridge-mode
  # limitation - only other LAN hosts can) - not a problem here, since
  # the router's own local DNS resolution (networking.nameservers)
  # stays pointed at dnsmasq, not Pi-hole.
  systemd.services.podman-network-pihole = {
    description = "Create the macvlan network the Pi-hole container attaches to";
    after = [ "network-online.target" "systemd-networkd.service" ];
    wants = [ "network-online.target" ];
    # "podman-pihole.service" is the container service Task 2 creates -
    # NixOS's oci-containers module names it "${backend}-${name}.service"
    # by default (confirmed against the module source).
    before = [ "podman-pihole.service" ];
    requiredBy = [ "podman-pihole.service" ];
    path = [ pkgs.podman ];
    serviceConfig = {
      Type = "oneshot";
      RemainAfterExit = true;
    };
    script = ''
      podman network exists ${piholeNet} || \
        podman network create -d macvlan \
          -o parent=${lanIface} \
          --subnet=10.0.0.0/24 --gateway=10.0.0.1 \
          ${piholeNet}
    '';
  };
}
```

### Task 2b: Fix Pi-hole's macvlan gateway reachability via a host-side shim interface

**Context (why this task exists):** Task 2's live verification found that the `pihole` container cannot reach `10.0.0.1` (the router) at all - confirmed via `tcpdump`-captured ARP timeouts, the router failing to ping the container back, and `wget`/`dig` failures from inside the container. This is macvlan bridge-mode's host↔child isolation, and it's **bidirectional** - Task 1 only anticipated the router-can't-reach-container direction. Since `10.0.0.1` is both Pi-hole's default gateway (all upstream DNS/gravity) and its conditional-forwarding target (`callan.local`/`srvr.farm`/reverse zone), DNS is currently completely non-functional. Full evidence: `.superpowers/sdd/2026-08-11-pihole/task-2-report.md`.

**The fix:** macvlan *siblings* on the same parent device *can* reach each other (only parent↔child is isolated) - so add a second, host-side macvlan interface (`pihole-shim`, `10.0.0.254`) on the router itself, same parent (`br-lan`) as the Pi-hole container's own macvlan network. Point Pi-hole's gateway and conditional-forwarding target at `10.0.0.254` instead of `10.0.0.1`, and have dnsmasq listen there too.

**Files:**
- Modify: `modules/network.nix` (new macvlan shim interface)
- Modify: `modules/pihole.nix` (new podman network gateway; forwarding targets)
- Modify: `modules/dhcp-dns.nix` (dnsmasq listens on the shim too)
- Modify: `modules/firewall.nix` (accept rules for the new interface, in **both** `input` and `forward` chains - see the chain-placement note in Step 4)

**Interfaces:**
- Consumes: the `pihole` container and `pihole-net` from Tasks 1/2.
- Produces: a working DNS path for the `pihole` container. No change to anything LAN-client-facing - `dns-failover`'s bypass target (`10.0.0.1`, for LAN *clients*) is untouched and was never actually broken (ordinary LAN hosts aren't macvlan children).

      current_gw=$(podman network inspect ${piholeNet} --format '{{range .Subnets}}{{.Gateway}}{{end}}' 2>/dev/null || true)
      if [ "$current_gw" != "10.0.0.254" ]; then
        # A container attached to this network blocks removing it -
        # explicitly remove it first. It'll be recreated by
        # podman-pihole.service's own pre-start, which already does
        # this unconditionally on every start regardless (this is

          -o parent=${lanIface} \
          --subnet=10.0.0.0/24 --gateway=10.0.0.254 \
          ${piholeNet}
      fi
    '';
```

(This makes the fix self-applying on the next deploy - no manual `podman network rm` needed on the live router - and self-healing/idempotent if this script ever runs again with the gateway already correct.)

Modify `modules/firewall.nix`'s nftables ruleset string in **two places** - the distinction matters and both are required:
- Traffic *addressed directly to* `10.0.0.254` (e.g. Pi-hole's conditional-forwarding DNS queries to dnsmasq) is locally-destined and hits the **`input`** chain.
- Traffic merely *routed via* `10.0.0.254` as a gateway, whose actual destination is elsewhere (e.g. Pi-hole's own upstream internet DNS queries to `1.1.1.1`) is **not** locally-destined and hits the **`forward`** chain instead. Missing this one would leave local-domain lookups working while all external/ad-blocked lookups silently keep failing - both are needed.

In `chain input`, change:

```
        # LAN and Tailscale are fully trusted, matching OPNsense's
        # allow-all floating rules for LAN_GROUP/opt5/opt2.
        iifname "br-lan" accept
        iifname "tailscale0" accept

        icmp type echo-request accept
```

to:

```
        # LAN and Tailscale are fully trusted, matching OPNsense's
        # allow-all floating rules for LAN_GROUP/opt5/opt2.
        iifname "br-lan" accept
        iifname "tailscale0" accept

        # pihole-shim: DNS queries from the Pi-hole container arriving
        # addressed directly to this router (10.0.0.254) - e.g. its
        # conditional-forwarding queries for callan.local/srvr.farm/the
        # reverse zone to dnsmasq. Traffic merely ROUTED via this
        # interface as a gateway (not addressed to 10.0.0.254 itself)
        # hits the forward chain instead - see below.
        iifname "pihole-shim" accept

        icmp type echo-request accept
```

In `chain forward`, change:

```
        # LAN can reach anything (WAN, Tailscale) - matches the "Any
        # Internal"/LAN_GROUP allow-all floating rules.
        iifname "br-lan" accept

        # Tailscale subnet-router/exit-node traffic in both directions.
        iifname "tailscale0" accept
        oifname "tailscale0" accept
```

to:

```
        # LAN can reach anything (WAN, Tailscale) - matches the "Any
        # Internal"/LAN_GROUP allow-all floating rules.
        iifname "br-lan" accept

        # pihole-shim: lets the Pi-hole container's own internet-bound
        # traffic (upstream DNS resolution, gravity blocklist download)
        # get routed out via wan - this is traffic merely using
        # 10.0.0.254 as its next-hop gateway, not addressed to

- [ ] **Step 1: Create `scripts/dns-failover.sh`**

```bash
# Switches the LAN's DHCP-advertised DNS server between Pi-hole and a
# direct/unfiltered path (dnsmasq itself, forwarding straight upstream),
# for when the Pi-hole container is down/unreachable and LAN DNS needs to
# work right now. Run `dns-failover --help` for details.
#
# Packaged via modules/dhcp-tools.nix (pkgs.writeShellApplication), which
# supplies the shebang, `set -euo pipefail`, and a curated PATH - this
# file is a script *body*, not a standalone executable.

DNS_SERVER_CONF="/var/lib/dnsmasq/dns-server.conf"
PIHOLE_IP="10.0.0.53"
DIRECT_IP="10.0.0.1"
prog="dns-failover"

usage() {
  cat <<EOF
Usage:
  $prog status
  $prog pihole
  $prog bypass
  $prog --help

Switches which IP address DHCP hands out to LAN clients as their DNS
server, by rewriting $DNS_SERVER_CONF and restarting dnsmasq. This is the
emergency escape hatch for when the Pi-hole container itself is down or
unreachable - NOT the same as pausing ad-blocking (see pihole-toggle for
that, which is faster and doesn't touch DHCP at all).

Commands:
  status   Show which IP is currently being handed out.
  pihole   Hand out $PIHOLE_IP (Pi-hole) - the normal/steady state.
  bypass   Hand out $DIRECT_IP (dnsmasq itself, forwarding straight
           upstream, unfiltered) - use when Pi-hole is broken/down.

Both pihole/bypass restart dnsmasq (a sub-second blip) to apply the
change - dhcp-option values aren't SIGHUP-reloadable, unlike static DHCP
reservations (see dhcp-static). Devices that already hold a lease keep
using whatever DNS server they were handed until their lease renews (up
to 12h) - this doesn't force clients to pick up the change early.

Requires root (restarts a system service) - run with sudo.

Examples:
  $prog status
  sudo $prog bypass    # Pi-hole down - get LAN DNS working again now
  sudo $prog pihole    # Pi-hole's back - switch back
EOF
}

die() {
  echo "$prog: $*" >&2
  exit 1
}

require_root() {
  if [ "$(id -u)" -ne 0 ]; then
    die "'$1' requires root - re-run with sudo."
  fi
}

current_ip() {
  [ -f "$DNS_SERVER_CONF" ] || { echo ""; return; }
  grep -oE '[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+' "$DNS_SERVER_CONF" | head -n1
}

cmd_status() {
  local ip; ip="$(current_ip)"
  case "$ip" in
    "$PIHOLE_IP") echo "Currently handing out: $PIHOLE_IP (Pi-hole)" ;;
    "$DIRECT_IP") echo "Currently handing out: $DIRECT_IP (direct/bypass - dnsmasq, unfiltered)" ;;
    "") echo "No DNS server configured yet ($DNS_SERVER_CONF missing or empty)." ;;
    *) echo "Currently handing out: $ip (unrecognized - neither the known Pi-hole nor direct IP)" ;;
  esac
}

set_ip() {
  local ip="$1" who="$2"
  require_root "$who"
  printf 'dhcp-option=option:dns-server,%s\n' "$ip" > "$DNS_SERVER_CONF"
  chmod 0644 "$DNS_SERVER_CONF"
  systemctl restart dnsmasq
  echo "Now handing out: $ip"
}

cmd_pihole() {
  if ! timeout 2 bash -c "echo > /dev/tcp/$PIHOLE_IP/53" 2>/dev/null; then
    echo "Warning: $PIHOLE_IP:53 doesn't seem reachable right now - switching anyway, but double check Pi-hole is actually up." >&2
  fi
  set_ip "$PIHOLE_IP" pihole
}

cmd_bypass() {
  set_ip "$DIRECT_IP" bypass
}

cmd="${1:-status}"
case "$cmd" in
  -h|--help) usage; exit 0 ;;
  status) cmd_status ;;
  pihole) cmd_pihole ;;
  bypass) cmd_bypass ;;
  *) usage; exit 1 ;;
esac
```

- [ ] **Step 2: Create `scripts/pihole-toggle.sh`**

```bash
# Pauses/resumes Pi-hole's ad/tracker blocking without touching DHCP or
# restarting anything - Pi-hole keeps serving DNS normally the whole
# time, just without (or with) filtering. Run `pihole-toggle --help` for
# details.
#
# Packaged via modules/pihole.nix (pkgs.writeShellApplication), which
# supplies the shebang, `set -euo pipefail`, and a curated PATH - this
# file is a script *body*, not a standalone executable.

prog="pihole-toggle"

usage() {
  cat <<EOF
Usage:
  $prog status
  $prog on
  $prog off [duration]
  $prog --help

Pauses or resumes Pi-hole's blocklist filtering, via 'podman exec pihole
pihole disable/enable'. Pi-hole keeps answering DNS queries the entire
time either way - this only toggles whether it filters them. Fast, no
service interruption. Good for "is this broken because Pi-hole is
blocking it, or something else."

This is NOT the tool for when Pi-hole itself is down/unreachable - see
dns-failover for that (it reroutes DHCP away from Pi-hole entirely).

Requires root - the container is managed by the system (root) Podman
instance, not a per-user one, so 'podman exec' needs sudo regardless of
which subcommand you run.

Commands:
  status          Show whether blocking is currently on or off.
  on              Resume blocking.
  off [duration]  Pause blocking. Optional duration (Pi-hole's own
                  syntax, e.g. '5m', '30s') auto-resumes after that long;
                  with no duration, stays off until 'on' is run.

Examples:
  sudo $prog off 5m     # quick "is it Pi-hole" check
  sudo $prog off        # pause indefinitely
  sudo $prog on
  sudo $prog status
EOF
}

die() {
  echo "$prog: $*" >&2
  exit 1
}

require_root() {
  if [ "$(id -u)" -ne 0 ]; then
    die "'$1' requires root - re-run with sudo."
  fi
}

cmd_status() {
  require_root status
  podman exec pihole pihole status
}

cmd_on() {
  require_root on
  podman exec pihole pihole enable
}

cmd_off() {
  require_root off
  local duration="${1:-}"
  if [ -n "$duration" ]; then
    podman exec pihole pihole disable "$duration"
  else
    podman exec pihole pihole disable
  fi
}

cmd="${1:-status}"
case "$cmd" in
  -h|--help) usage; exit 0 ;;
esac
[ $# -gt 0 ] && shift

case "$cmd" in
  status) cmd_status ;;
  on) cmd_on ;;
  off) cmd_off "$@" ;;
  *) usage; exit 1 ;;
esac
```
